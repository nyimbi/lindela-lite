## B1. The registration guards are blind to the defect they name, and break on the fix

**Clean `HEAD` is green: 370 tests, 370 pass, 0 fail.** Stating that plainly,
because the finding below is not "the build is red". It is worse than that.

Two tests, at `test/lite.test.js:5462` and `test/lite.test.js:5519`, both named
`registers the source end to end`, both guard the connector-registration bug class
this repository has now hit three times:

```js
const ingestionSource = await fs.readFile('src/ingestion.js', 'utf8')
assert.ok(ingestionSource.includes('food_security_records: []'),
  'runIngestion drops collections missing from its merged map')
```

They assert that a **string appears in a file**. The defect they were written for is
real and still present at `HEAD` (D1 below): `countRecords` reads four collections
while the merge accumulator handles six.

The problem is that the assertion reads the wrong half of the file. It greps the
accumulator, which is correct. The bug is in `countRecords`, fifty lines away. The
test passes with D1 fully present.

To confirm rather than reason, the accumulator was refactored to derive itself from
the same shared `OUTPUT_COLLECTIONS` list `countRecords` uses. That change **fixes
D1**. Both tests immediately failed:

```
AssertionError: runIngestion drops collections missing from its merged map
  assert.ok(ingestionSource.includes('disease_observations: []'))
```

So the guard is simultaneously blind to the defect in its own failure message, and
brittle to any refactor of the accumulator, including the correct one. A green build
here is not evidence that the ingestion path is correct. A green build is evidence
that a particular string is still present.

**Fix:** assert on behaviour. Run ingestion with a stub connector that returns a
`disease_observations` array, then assert the records come back out of the store and
that `records_by_collection` reports the same count. That catches a dropped
collection, catches the counting bug, and survives any refactor.

Every registration guard in this repository has this shape — `COLLECTIONS` in
`store.js`, the merged map in `ingestion.js`, the doc tables regenerated by
`scripts/validate.mjs`. Each asserts on source text because the map it cares about
is not exported. Export the list and assert on it, or assert on behaviour. Do not
assert on spelling.


## D1. `countRecords` reads four collections while ingestion merges six

Committed state, `git show HEAD:src/ingestion.js:334-342`:

```js
function countRecords(output) {
  return ['climate_observations', 'hazard_events', 'conflict_events', 'service_assets']
    .reduce((total, key) => total + (output?.[key]?.length || 0), 0)
}

function countRecordsByCollection(output) {
  return Object.fromEntries(['climate_observations', 'hazard_events', 'conflict_events', 'service_assets']
    .map((key) => [key, output?.[key]?.length || 0]))
}
```

The merge accumulator at `src/ingestion.js:105-111` merges six, adding
`food_security_records` and `disease_observations`. The two counters know about
four.

**Failure scenario.** Ingest `ipc_hdx`, which returns only `food_security_records`.
`countRecords(output)` is `0`. `recordsProcessed` is `0`, and the source policy's
`minimum_records` gate never clears, so a run that fetched several hundred IPC
acute-food-insecurity classifications reports:

```
degraded — Expected at least 1 records; received 0
```

The same applies to `who_gho` and its `disease_observations`. Ingestion reports
failure while succeeding, on the two newest and most operationally important
sources. An operator watching source health sees a healthy food-security pipeline
as broken, and learns to ignore the health signal. This is the worst failure
direction: it does not lose data, it destroys trust in the instrument that would
have told you data was lost.

Note the consequence for the fix in B1: the correct fix is exactly the one the
test reacted badly to — derive all three consumers from one list.

## D2. `PostgresStore.replaceAnalytics` silently discards the impact figures

Committed state, `git show HEAD:src/postgres-store.js:164`:

```js
async replaceAnalytics({ risk_scores = [], impact_assessments = [], data_quality = [], road_access = [] }) {
  return this.merge({ risk_scores, impact_assessments, data_quality, road_access })
}
```

`JsonStore.replaceAnalytics` at `src/store.js:86` takes six collections. The
caller at `src/analytics.js:21` passes all six:

```js
await store.replaceAnalytics({
  risk_scores, impact_assessments, data_quality, population_at_risk, facilities_at_risk, road_access
})
```

Two independent defects in three lines:

**D2a — dropped collections.** On the Postgres backend, `population_at_risk` and
`facilities_at_risk` are computed, passed in, and never written. Impact-based
forecasting — people at risk, facilities at risk — is exactly the capability that
moves WMO and IFRC practice from hazard intensity to consequence. It works on the
JSON backend and is silently absent on Postgres. Postgres is the *default*
backend in every deployment that sets `LINDELA_LITE_DATABASE_URL` or `DATABASE_URL`,
which is the documented production path.

**D2b — merge where replace was meant.** It delegates to `merge()`, the opposite
operation. A region that stops qualifying — out of scope, inputs withdrawn — keeps
its last computed `risk_scores` row forever. The JSON store replaces. So the two
backends disagree about whether stale analytics survive, and the disagreement is
determined by an environment variable.

**Why this survived:** see B3. The module containing it has no meaningful tests.

**Fix:** delete-then-insert per collection inside one transaction, with the same
six-collection signature as `JsonStore`, and assert both backends agree in a
shared conformance suite.

Two mechanisms conspire:

1. The `test:coverage` script in `package.json` enumerates five test files and
   does not include `test/database.integration.test.js`. The CI coverage job
   runs that same script, so the coverage gate never executes the Postgres path.
2. `npm test` on this machine reports `external PostgreSQL integration # SKIP`
   and `pg0 integration # SKIP`. The integration tests are opt-in
   (`LINDELA_LITE_TEST_PG0=1`), so on a default CI run they do not run either.

Net effect: **in CI, `postgres-store.js` has 0% function coverage and 23% line
coverage, on the backend that every production deployment uses.** D2 lives
precisely there.

Two further gaps the aggregate hides:

- `auth.js` at 47% branch coverage, with lines 43-46, 49-54, 61-62, 65-66, 69-70
  and 75-76 uncovered. Those are the scope-mapping and comparison branches. Auth
  is the one module where an untested branch is a vulnerability, not a gap.
- `alerts.js` at 41.58% branch with lines 164-224 uncovered — the approval gate,
  trigger protocols, backtest and shadow-mode region. That is the
  human-in-the-loop control described in `README.md` as a product commitment.

## B4. `/metrics` is served before the auth gate

`src/server.js:105-113`:

```js
if (url.pathname === '/metrics' || url.pathname === '/api/v1/metrics') {
  res.writeHead(200, { 'content-type': 'text/plain; version=0.0.4', 'cache-control': 'no-store' })
  res.end(metrics.render())
  return
}
if (url.pathname.startsWith('/api/v1/')) {
  await handleApi(await storeProvider, req, res, url)
  return
}
```

Auth lives in `handleApi`. The metrics branch returns before reaching it, so
`/api/v1/metrics` is unauthenticated despite being under `/api/v1/` — a route
namespace whose every other member is gated. Leaked to an unauthenticated
caller: request rates, error rates, latency percentiles and route labels. Route
labels are an enumeration aid. Low sensitivity, but it is a control that looks
present in the namespace and is absent in fact.

## D3. Internal error messages are returned verbatim to clients

`src/server.js:118-122`:

```js
} catch (error) {
  jsonResponse(res, error.statusCode || 500, {
    success: false,
    error: error.message || 'Internal server error',
  })
}
```

Any thrown value's `message` reaches the client. In this codebase that includes
failures from `pg` (which routinely carry the connection string, the failing
statement text, and constraint names), from `JSON.parse` (which carry a fragment
of the offending payload), and from filesystem calls (which carry absolute
paths). A 500 becomes an information disclosure primitive.

**Fix:** log `error.stack` server-side with a correlation id; return the id and a
generic message to the client.

## D4. `docs/openapi.yaml` is incomplete and internally asymmetric

48 literal `/api/v1/*` path checks exist in `src/server.js`. `docs/openapi.yaml`
declares 99 paths (many are parameterised). Nine literal routes have no spec entry:

```
/api/v1/demo/seed
/api/v1/disease-observations/summary
/api/v1/districts
/api/v1/impact/facilities-at-risk
/api/v1/kpi/monthly-series
/api/v1/kpi/quarterly.pdf
/api/v1/kpi/refresh-snapshots
/api/v1/kpi/snapshots
/api/v1/metrics
```

The asymmetry is the tell. `docs/openapi.yaml:129` documents
`/api/v1/impact/population-at-risk`, while `/api/v1/impact/facilities-at-risk`
is absent. `/api/v1/disease-observations` is documented (line 675) but its
`/summary` sibling is not. These are sibling endpoints added in different
commits, and the spec was updated for one and not the other.

The OpenAPI file is the integrator's contract. Drift in it is not cosmetic: it
means an integrator who builds against the spec never learns half the KPI
surface exists.

**Fix:** generate the path list from the router, diff against the spec in CI,
fail the build on drift. Hand-maintained API specs rot; this one already has.

## Working-tree contamination during this audit

While the domain agents were running, four tracked files were modified without
being asked for:

```
 docs/architecture/ingestion.md |  2 +-
 src/analytics.js               | 18 ++++++++++++++-
 src/ingestion.js               | 32 ++++++++++++++++++--------
 src/postgres-store.js          | 52 ++++++++++++++++++++++++++++++++++++--
```

The changes are correct and correspond exactly to D1 and D2, and the refactor is
what exposed B1: applying it makes two tests fail. They were reverted and preserved
as `docs/improvements/proposed-fixes.patch` so the audit stays reproducible from a
clean tree.

**If you apply the patch, rewrite those two tests in the same change.** The patch
as generated re-anchors the source-text grep onto the new list, which makes the
build green again without making the test any better. Replace them with a
behavioural assertion as described in B1, or the next correct refactor will break
them again.

For the record, `main` is green at `HEAD`: **370 tests, 370 pass, 0 fail**. An
earlier reading of this audit reported two failures; that measurement was taken
with these edits applied and is retracted.
